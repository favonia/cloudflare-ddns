# Design Note: Notification Model

Read when: deciding notification triggers, first-known address coverage, observation differences, lifecycle grouping, or evidence and uncertainty claims.

Defines: notification design principles and their lifecycle assumptions. These guide notification changes; they are not a claim that every derived behavior is already implemented.

Presentation tradeoffs and candidate refinements are discussed in [Notification Messages rationale](../../rationale/notification-messages.markdown). That discussion does not change this model’s contracts.

## Events and Context

Notify about meaningful changes to managed content or service lifecycle, pending, failed or unconfirmed work, and newly observed address differences that the updater's own work cannot explain. Include enough known state to help the recipient understand the event.

Decide the trigger separately from its content. Previous addresses explain a transition; they need not create a new trigger. Determine operation outcomes from the operation contract, not address equality or the presence of formatted text. A successful no-op stays silent unless lifecycle context, missing first-known address context, or a newly unexplained observation justifies a notification.

Previous addresses are the managed DNS address set admitted as input to the operation, possibly from a valid cache. They are distinct from the previous detected public IP and the desired target. `static.empty` requests clearing: removal is a change, while already-empty successful assessment is a no-op. `none` leaves that family outside management and supplies no empty observation.

## Lifecycle and Composition

A scheduled process provides an ongoing service. Its startup and shutdown are meaningful lifecycle events. A one-shot invocation performs one operation; its ordinary process entry and exit are not separate service events. This distinction keeps externally scheduled one-shot runs from generating lifecycle noise.

One operation round contributes at most one notification envelope, combining relevant observations, first-known address context, and operation outcomes. A scheduled startup or shutdown flow incorporates its associated round or cleanup in its lifecycle envelope:

- With an immediate update, wait for the first round and combine startup with all assessed domain/family results and relevant WAF outcomes, including no-op and failures. Without an immediate update, report startup without inventing an address observation.
- Scheduled shutdown combines stopped context with cleanup outcomes, including pending or unconfirmed work. With cleanup disabled, report stopping without implying that managed content is empty.
- If no future execution can be scheduled, combine the scheduling failure with cleanup outcomes.
- `@once` reports its operation result without startup/shutdown context, deferred first-known coverage, or cross-round inference. An ordinary successful no-op stays silent. With `DELETE_ON_STOP=true`, it runs direct cleanup with the existing completion wait instead of an extra update.
- A handled signal during the immediate round preserves startup plus the actual interrupted or partial result, followed by a separate stopped/cleanup envelope. These are distinct lifecycle events; interruption must not discard successful partial work or imply a completed round.

Choose a primary notification kind without losing constituent failures. An associated update or cleanup failure takes its operation-failure kind rather than a successful lifecycle kind; an initial update failure is not a configuration/startup failure. Successful startup and shutdown envelopes use their lifecycle kinds. Scheduling failure takes priority on its exit path, with any cleanup failure retained explicitly. Ordinary operation kinds remain unchanged. An envelope containing only first-known context or unexplained observations uses a state-observation kind that does not imply a mutation.

Keep work, waiting, cancellation, heartbeat, and exit-status contracts in the [Lifecycle Model](lifecycle-model.markdown) independent of notification grouping. Notification delivery does not determine work success.

## First-Known Address Coverage

For a scheduled process, track first-known address context independently for each domain/IP family under a stable ownership scope. This is the first usable pre-operation address information included in a notification during this process; a later read does not reconstruct addresses at process startup.

A failed initial read leaves that scope uncovered while other scopes can be reported normally. When missing context becomes available later, include it once, even on no-op, without adding unrelated already-covered no-op scopes.

Coverage advances only when a nonempty envelope completely representing that scope's admitted pre-operation address information is submitted to `Notifier.Send`, irrespective of its delivery Boolean. Representation may be distributed across Removed, Unchanged, old update operands, and explicit context; it does not require a literal Before field. A complete delta from explicitly known-empty input may represent that empty context. Known-empty and historical input attached to a failure count when fully represented; a desired target alone does not. Obtaining a snapshot or omitting known facts during rendering does not count. A conservative fallback must preserve undisplayed facts or leave coverage unset. This disclosure test does not remove selected failures or other notification scopes. Coverage does not reset after cache expiry, later failure, or address changes. Keep it process-local, with no persistent history or delivery retries.

## Observation Differences

Keep observation inference separate from first-known coverage and delivery. For each domain/family, retain the latest admitted fresh remote observation and the completed effects or possible completed outcomes of subsequent own mutations. Compare a fresh pre-operation read with that model before applying this round's writes.

A compatible observation needs no extra observation-change notification and does not establish which request caused it. An observation outside the model supports reporting an unexplained address difference, even if reconciliation is a no-op. It does not identify an external actor. Describe the detected unexpected address change before this round's operation or no-op outcome, so it cannot be mistaken for a description of this process's own write. Describe returned comment-selector mismatch as exclusion from management immediately after the associated completed operation. This evidence does not establish a previous server comment. Record identities and duplicate multiplicity support inference; changes to them alone are not address-change triggers.

After either comparison result, replace the baseline and accumulated alternatives with the actual fresh observation. This resolves current-state uncertainty without proving whether an earlier unconfirmed request succeeded. Repeated unchanged reads therefore do not repeat the discrepancy, and old addresses gain no permanent exemption from comparison. Failed or invalid reads supply no new baseline; valid cached input is historical operation evidence, not an independent fresh observation. Cache expiration alone creates no notification trigger.

Inference must admit every possible completed own outcome so approximation cannot manufacture a discrepancy. Keep uncertainty local and storage bounded, with conservative widening when precision cannot be retained. Keep the representation, analysis budget, and aliasing rationale with their owning code.

## Evidence and Uncertainty

State reports describe evidence obtained for the operation. They do not certify live remote state at delivery time. Do not add provider or API reads solely to enrich a notification.

Keep known-empty distinct from unknown, observed addresses distinct from desired targets, and unattempted work distinct from no-op. An acknowledged DNS mutation supports reporting its completed effect; it does not imply a fresh read-back or prove exact final managed membership when returned metadata changes ownership. A pre-operation snapshot remains historical after an uncertain mutation and may accompany an unconfirmed result without being presented as final state.

Completed creation and update remain successful when the returned comment falls outside the managed selector. Creation admits only matching returned comments to the managed cache, consistent with update eviction; creation still caches requested metadata for admitted records. A later fresh matching read can readmit an excluded record. The configured pipeline validates requested comments against the selector, so an unexpected nonmatching return differs from the requested comment. Unknown or unconfirmed membership does not support exclusion.

A partial operation reports confirmed effects and effects whose completion could not be confirmed; it does not establish that the whole managed address set equals the successfully written subset. Keep pre-operation addresses as shared historical context. Already-satisfied targets, a prerequisite-blocked request, and required work not attempted after an earlier failure are different outcomes. The absence of a possible mutation effect cannot distinguish them.

The setter owns the progress evidence needed to report these distinctions, separately from effects used for own-change inference. Reporting must not reconstruct reconciliation by subtracting effects from target sets. Preserve deletion-stage failures even after all writes succeed; deleting one record does not imply that its address disappeared when duplicates remain. Deletion progress retains the association between each record and its address and distinguishes confirmed, unconfirmed, prerequisite-blocked and unvisited removals. Keep distinct record outcomes even when addresses coincide; the recipient need not see record IDs. This permits specific attempted-versus-unvisited deletion summaries without inventing counts or claiming whole-address removal. Progress reporting follows existing execution policy, including scope-local fail-fast reconciliation and cleanup continuation until its existing cancellation boundary; it does not change that policy.

## Content and Operation Results

Present one block per scope, separated by blank lines, in lifecycle, IPv4 DNS, IPv6 DNS, then WAF order. Keep domain/family identity visible. Preserve useful results for successful domains alongside failures elsewhere. Group domains only when outcome, source, relevant input and target sets, uncertainty, and observation context agree; a shared target alone is insufficient. Canonicalize address sets and evaluate scope-specific evidence before grouping.

For confirmed successful reconciliation, describe content relative to admitted input with Added, Removed, and Unchanged sets. Exactly one removed and one added value use `Updated: old → new`, with retained values separate; otherwise use Added and Removed. Use English conjunctions and Oxford commas without braces or square brackets. These are content deltas, not HTTP methods or a live read-back guarantee. Record identity and membership evidence must support unique-address removal; metadata or comment-membership anomalies remain operation outcomes. Complete pure additions include an only/all managed-address conclusion; confirmed complete removals include an explicit no-managed-addresses-remain conclusion. Mixed deltas, a single replacement, and nonempty Unchanged do not need a general inventory ending.

For incomplete DNS work, use short Update confirmed, Update unconfirmed, Update blocked, and Update not attempted labels, with one evidenced old-to-new operation pair per line. Do not add an operation heading or vary the Update label with multiplicity. True creations and deletions use Addition and Removal status. Pairing comes from operation evidence, never sorted sets. An individual completed operation does not establish whole-scope success while work or membership remains unresolved. Preserve a conservative context fallback when identity is missing or conflicting. Omit repeated Target/Before fields only when operation facts and retained content fully convey that information.

Selected no-change observations use Current; ordinary covered no-op remains silent. After an unexpected address-change event, use `No IPv4 update needed` or `No IPv6 update needed` instead of repeating Current when there was no mutation. Before any identified operation, a known nonempty desired target uses `Could not start the update to` followed by those addresses; unknown input with an empty target uses Cleanup blocked without inventing empty contents. Known-empty partial input uses a Current observation before any completed or unconfirmed mutation, and a no-addresses-before-the-update sentence afterward. Nonempty historical context identifies addresses before the update or cleanup, with cache provenance retained. Unknown and known-empty remain distinct.

### Source and Counts

Retain admitted-input provenance through rendering and grouping. Uniformly cached Removed, Unchanged, and partial-removal old-address groups carry one `(cached)` marker on the group; arrows mark only the old operand. Current may describe cached input with its source marked. Cache validity is evaluated at admission: cached identifies evidence source, not uncertainty of a confirmed operation. A failed or partial operation must not present an inferred After state as Current. Resource headings identify the domain/family or list without scope parentheses. When configured ownership is restricted, current inventory labels explicitly name managed addresses or managed items; an empty observation uses none. Historical labels and empty-history sentences identify the same managed scope and the update or cleanup they precede. Unrestricted observations may retain the shorter labels.

DNS operation counts use distinct trustworthy record identities within each IP/status bucket. Omit a plain count of one only when a complete trustworthy admitted owned snapshot establishes exactly one record with that IP in the original scope. Otherwise retain a trustworthy one; knowing how many deletions occurred does not establish overall same-IP multiplicity. Retain plural counts, omit zero buckets, and never invent counts from missing or conflicting identity/cardinality. Check each original scope independently before grouping, without summing across domains or inferring snapshot completeness from omitted display rows. This rule does not change successful Removed content summaries or prove whole-address disappearance.

An other-record qualifier requires an earlier visible trustworthy per-record update pair for the same old IP, original scope, round, and block. Removal identities must be disjoint from every qualifying update identity. Current, Before, content-level Updated, earlier removals, later rows, and other scopes are not anchors. Without an anchor, use a plain trustworthy count; missing anchor evidence and missing count evidence are separate cases. Preserve qualifying other-record wording even for one record. Cleanup has no update anchor and uses plain counts.

Duplicate-content and multiplicity cases remain defensive contract inputs. Local fixtures and control-flow checks do not establish that same-zone/name/type/IP duplicates are admissible service states. Neither assume those states are production-reachable nor assert universal remote uniqueness across metadata variants and update paths.

## WAF Evidence

WAF reports use actual prefixes from already-read owned input and supported returned or operation evidence. Targets are coverage requirements, not actual list contents: a covering prefix may satisfy a narrower target. Preserve missing-list, known-empty owned selection, and unknown-input distinctions, plus cache provenance. A missing-list observation uses Current only while current; historical absence says the list did not exist before the update or cleanup. Do not add reads to enrich notifications, cross-round WAF inference, or WAF first-known coverage tracking.

The notification's managed WAF inventory is the comment-selected snapshot projected to configured families. Reporting retains family scope even when the selected inventory is empty: an owned empty family differs from a family outside ownership. One scope entry per configured family records whether it is selected for this operation; selection does not imply dispatch or completion. Updates select families with available targets. Shutdown cleanup selects every configured family, while evidence analysis can describe a narrower cleanup selection without treating it as complete cleanup of the broader scope. Never-configured families are omitted, even when the API snapshot contains them. Confirmed reconciliation deltas and Unchanged include only successfully reconciled active families. Temporarily unavailable configured families remain outside those claims, with their adjacent detection failure retained. Beside a successful active-family delta, show a trustworthy current observation for each configured inactive family, including known empty; if only admitted historical evidence exists, identify its time instead. An existing whole configured-scope Current or historical inventory already covers those families and needs no duplicate family rows. A selected no-op Current observation shows configured inventory, including unavailable configured families.

Configured partial ownership means a nonempty comment selector or an omitted configured family. Temporary detection availability and shutdown-deletion policy do not change it. WAF inventory uses item(s), including range-valued items. Complete pure additions use only/all conclusions, scoped to the active family when an inactive-family observation follows; complete removals use a no-managed-items-remain conclusion within the supported scope. Only/all eligibility depends on complete trustworthy item identities, never just deduplicated prefix counts. Multiple valid IDs sharing one prefix use a counted inventory instead of claiming one item. Empty-state claims apply to the managed scope and never imply deletion of the physical list.

WAF mutations carry batch-level evidence separating blocked prerequisites, uncertain attempted work, and supported completion. Render grouped Addition/Removal status labels without the word batch; a failed batch cannot support separately confirmed per-prefix outcomes. Preserve the existing create-before-delete sequence, including a create failure stopping deletion and a delete failure after successful creation. Retain planned and actual returned evidence needed to distinguish operation completion from managed-content membership; parsing or membership problems cannot silently become successful content deltas. Work-result projections remain separate from descriptive evidence. Structural list creation dispatched without confirmation is a distinct `List creation unconfirmed` outcome even when item work is blocked. Prior input can remain Current only when no later content or structural mutation was dispatched.

A trustworthy terminal returned configured inventory is independently usable even when membership inconsistency prevents a successful delta. Later possible content or structural mutation makes that inventory historical; an empty or otherwise NoEffect batch does not. Preserve operation rows and show the usable terminal Current inventory, without a generic whole-content uncertainty summary. Completed responses with unusable parsed data or unreliable identities receive their specific explanation beside the revealing operation. Unconfirmed operation rows already carry their uncertainty. Supported exclusions of previously managed IDs report the unexpectedly changed comment and its failure to match the filter immediately after the revealing batch; prefix equality alone cannot identify a newly created item or justify an exclusion warning. A terminal empty inventory after an addition is an observation, not proof that a particular item was excluded.

Cleanup input is admitted before item cleanup. If whole-list deletion first fails, the existing fallback read occurs after that attempt; its snapshot is not input to the entire cleanup and must not be replayed against the earlier whole-list attempt. Preserve the failed attempt as evidence while allowing successful fallback to retain its successful work result.

DNS management operations are synchronous: an unconfirmed attempt may or may not have completed, rather than representing queued future work. Public DNS propagation and TTL do not turn completed management operations into pending writes. WAF operations can remain asynchronous under the existing cleanup waiting policy. Known completed cleanup may show removals; completed whole-list cleanup without admitted input uses Cleanup completed, and accepted unwaited cleanup uses Cleanup started. For accepted item cleanup, use one Cleanup started row with the actual prefix operands; without operands, retain standalone Cleanup started. When the targets equal all trustworthy configured input identities, combine that completeness fact with the operands instead of repeating the inventory. Cached full input uses an explicit historical only/all conclusion with its cached source marker. Partial targets retain historical input context and source, without an all claim. Preserve any preceding unconfirmed list-deletion stage as List deletion unconfirmed, distinct from subsequent item cleanup and its observed contents. Completed cleanup subtracts confirmed deleted identities before prefix projection: deleting one ID cannot erase a prefix retained by another ID. Pending exit cleanup is not confirmed completion. Reporting preserves existing calls, cache behavior, cancellation, and waiting policy.

## Contract Placement

API boundaries own admitted reads, cache-versus-remote evidence, returned-data ownership, and supported mutation effects. Setters own immutable pre-operation snapshots and progress for operations actually reached, including WAF planned batches and completion evidence. Updaters preserve intent, targets, partial DNS results, and WAF outcomes. Process-owned reporting below `cmd/ddns` owns inference, coverage, and semantic content selection; the composition root selects lifecycle context and submits envelopes without inspecting record internals or cache expiry. Notifiers format and deliver composed notifications through existing transports; domain-state rendering and grouping belong to the reporting layer.

Document snapshot ownership, copying, cache validity, result invariants, and caller obligations with the responsible types and functions. Exact wording and channel formatting follow [Operator Messages](../guides/operator-messages.markdown).
